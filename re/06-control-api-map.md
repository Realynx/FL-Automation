## Priority operations → native entry points (examples)
- **Piano-roll notes:** `addNote 0xB7E210`, `getNote 0xB7E0A0`, `deleteNote 0xB7E130`,
  `clearNotes 0xB7E470`, `getTimelineSelection 0xB7E790`, `getDefaultNoteProperties 0xB7E860`.
- **Channel step grid:** `channels.setGridBit` → `FL_py_channels_setGridBit 0xE02D30`
  → inner `FUN_00E2C350` (writes the step) via `FL_ResolveChannel 0xE05CB0`.
- **Playlist tracks:** `playlist.trackCount 0xDFD370`, `getTrackName/setTrackName`,
  `muteTrack/soloTrack/selectTrack`, `getTrackColor/setTrackColor` (`0xDFDxxx` cluster).
- **Mixer + params:** `plugins.setParamValue` → `FL_py_plugins_setParamValue 0xE270A0`
  → `FL_SetParamEventValue 0xE2C960`. Mixer tracks: array `@0x14A7EB0`, stride `0x1474`,
  10 FX-slot plugin ptrs `@+0x1324`; param-id = channel `base+idx+0x8000`, mixer-FX
  `FL_MixerEffectParamBase(0x11C23B0)+idx+0x70008000`.
- **Plugin/VST control:** `TBaseAudioPlugin` (VMT `0x84B138`) — **122 virtual methods**
  (`TBaseAudioPlugin.vtbl_0..121`), inherited by `TVSTPlugin`/`TVST3Plugin`/`TGenericPlugin`.
  This is the per-plugin param/process/state interface.

## IMPORTANT design note: call the *inner* engine funcs, not the `FLpy_*` wrappers
The `FLpy_<module>_<name>` functions are **PyCFunction wrappers** — they take
`(PyObject* self, args, kwargs)`, parse a Python tuple (via `PyArg_ParseTupleAndKeywords`
ptr `@0x14ABAC8`), then call the real engine routine. The injected DLL is **native, not
Python**, so it should:
1. Use `fl-py-methods.txt` as the **map** (which inner routine, what arguments, the
   param-id math, units like float×2^30) — this is its main value, *not* as a call target.
2. Call the **inner engine functions** directly (e.g. `FL_SetParamEventValue`,
   `FUN_00E2C350`, the note/playlist routines) and/or manipulate the **engine structs**
   (mixer-track array, channel/pattern/playlist models) — the complete, un-sandboxed surface.
3. Resolve everything from the **host-context root** stashed at global `0x14A7E40` (set by
   `CreateFruityInstance`) plus the known global arrays.

## Engine roots & structures known so far

## Central command dispatchers (Task #3, named in Ghidra)
Most parameterized operations route through a few central dispatchers:
- **`FL_DispatchOpEvent` (`0xE2C350`)** — `(contextObj, resultBuf, handlerFn, flag, args…)`.
  Used by `setGridBit` (handler `0xE02C80`) and `setCurrentTempo` (handler `0xE0A230`).
- **`FL_DispatchTransportOp` (`0xE2C790`)** — transport.start path: `(ctx, resultBuf, 10, 2, mode, 8)`.
- **`FL_SetParamEventValue` (`0xE2C960`)** — param/automation value setter.

To call directly we need: (a) the **real engine singleton** as `contextObj` — the Python-layer
context getters (`FUN_00e0c4d0` = `(*0x14A7DC0)()`) are **null at rest**, so use the engine's own
object reachable from host-context `0x14A7E40`; (b) a properly **constructed `resultBuf`**
(`FUN_00415610(buf, &DAT_00E28818)` builds it — likely a managed/record type, not raw memory);
(c) the per-op handler fn. This is the immediate next RE step toward a visible setter.
